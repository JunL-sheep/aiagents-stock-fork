# 项目改动日志（docs/change-logs/）

> 每次对项目做实质性改动，按日期归档在这里，便于回溯。
> 与根目录的 `docs/UPDATE_LOG.md`（单一连续追加）互补——本目录适合"一次改动一篇"的归档，便于跳转到 git diff、关联代码改动。

## 命名规范

`YYYY-MM-DD-<改动主题简述>.md`（kebab-case，主题用名词/动名词，避免太长）。

例：`2026-07-28-monitor-pool-injection.md`

## 每篇日志应包含的章节

1. **背景与用户决策**（为什么改、明确下来的设计选择，逐条列出）
2. **改动文件清单**（路径 + 关键变化一句话概括）
3. **关键行为 / 验收点**（哪些验证测试通过了，最好贴命令输出）
4. **踩坑 / 注意事项**（容易忘的边界、未来再改时要小心什么）
5. **相关文档链接**（项目内 `docs/` 里其他相关文档、代码文件）

## 何时该写一篇

- 引入新模块、新文件、新数据流
- 改了既有架构（监测池、定时任务、推送链路、调度器等）
- 加了数据库 schema 字段
- 重构了关键循环/服务（`monitor_service`、`scheduler` 等）

## 何时**不**写

- 微小修补（typo、文案调整、单行 bug）
- 仅依赖/版本号变更
- 文档本身的勘误

> 噪音少才有用，犹豫时倾向"不写"。
